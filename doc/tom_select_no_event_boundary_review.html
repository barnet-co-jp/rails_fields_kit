Tom Select No-event Boundary Review

Static QA lane for request cancellation and stale response boundaries. It keeps aborted or stale requests separate from visible loading and failure states, without changing runtime events, helper markup, retry UI, or host-app feedback policy.

Tom Select core states Events Visual reference map

Review focus

  • Compare loading, visible failure, and suppressed no-event states without treating no-event as a new UI component.
  • Confirm stale or aborted requests stay visually quiet and do not read like host-app-visible failures.
  • Keep success/failure event dispatch and request lifecycle details in the maintained events docs.

Host boundary

Current failure still belongs in feedback lanes

No-event is only for aborted or stale work. A current request failure can still use documented request-failure hooks.

request C startsQuery: support
request C failsDispatch failure event for the current request

Use this lane to avoid overcorrecting and hiding real current failures.

Checklist

  • No-event copy stays visually quieter than visible failure copy.
  • Loading, current failure, and stale/aborted no-event states are distinguishable at narrow width.
  • The suppressed state does not introduce retry prompts, fallback copy, or default failure UI.
  • Event names, payloads, retry UI, and request controller behavior are not changed by this artifact.

Non-goals

  • No request-start or request-finish event proposal.
  • No built-in retry, cancellation banner, toast, or fallback UI.
  • No production Tom Select styling or helper markup changes.

Scope note. This page is a static design and QA artifact. The maintained behavior contract remains in the events documentation and runtime tests. Use this page only to review whether stale or aborted request boundaries are readable without being confused for visible failure states.
